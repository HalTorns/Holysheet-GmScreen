## A. Droits Convex

### Inventaire exhaustif de la surface cliente

**76 fonctions publiques : 32 queries, 42 mutations, 2 actions ; aucun `httpAction` exporté par l’application.** Les routes HTTP Better Auth sont enregistrées dynamiquement par `registerRoutesLazy` (`convex/http.ts:6`) et sont revues en C ; elles ne sont pas des exports Convex nommés.

Le script analyse l’AST et les types des exports (alias et réexports inclus). Il reconnaît les retours enregistrés `isPublic`/`isHttp` et leur genre, y compris lorsqu’un builder personnalisé les produit. La lecture de `convex/lib` ne trouve actuellement aucun builder d’enregistrement personnalisé ; ses fonctions sont des helpers ordinaires. `_generated` est exclu du parcours ; les fichiers générés peuvent être chargés pour résoudre les types. Les sous-arbres portant leur propre `convex.config.ts` sont des composants isolés : `convex/betterAuth` n’est pas une API directement accessible au navigateur. Ses relais applicatifs sont tous inventoriés. Le composant rate-limiter installé reste hors sources applicatives.

Les colonnes auth/accès/bornes donnent des **indices AST**, avec appels transitifs aux helpers locaux de `convex/lib`, pas une preuve automatique d’autorisation. `args`/`returns` indiquent la présence syntaxique, pas la justesse du contrat. « — (revue manuelle) » ne signifie donc ni absence de contrôle ni liste illimitée. Le contrôle A6 exige une ligne fichier/export/type dans le bloc ci-dessous ; il ne garantit pas que l’analyse humaine reste à jour après changement du corps d’une fonction.

### Proposition d’ADR : migrations internes versionnées

Contexte : petite bêta, Convex auto-hébergé et données V1 à préserver ; aucun composant de migrations installé. **Recommandation : commencer par des migrations internes versionnées, paginées et idempotentes**, avec journal durable (identifiant de migration, curseur, état, compteurs), verrous/reprise et commande opérateur à cible explicite. Introduire d’abord les lecteurs compatibles ancien/nouveau ; migrer par lots, vérifier/exporter, puis retirer l’ancien format dans une livraison séparée. Un échec doit reprendre au dernier lot validé. Sauvegarde vérifiée avant application ; un rollback du code ne restaure pas les données.

Alternative `@convex-dev/migrations` : réduit le code de suivi/reprise à maintenir mais ajoute un composant, une dépendance et une matrice de compatibilité à vérifier sur le backend épinglé. Aucun besoin de parallélisme complexe établi aujourd’hui. Réexaminer ce choix si plusieurs migrations longues apparaissent ; ne pas installer le composant sur la seule foi de sa documentation actuelle. Cette recommandation décrit une architecture proposée, aucune API du paquet ni compatibilité de version n’a été validée.

Conséquences : plus de code interne à tester, mais pas de dépendance implicite ; tests au vrai point d’entrée interne avec documents V1, réexécution sans double effet, interruption/reprise et export final. A7 s’applique aussi au schéma Better Auth lors de sa future montée. Ne pas créer de table de journal ni modifier un schéma pendant cet audit.

### Hypothèse sur connexion/rechargement
