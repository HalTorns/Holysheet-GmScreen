# Widgets personnalisés — F8

Décision du 2 novembre 2026, [plan approuvé](../PLAN-F8.md). Les définitions appartiennent au compte et au projet ; les instances partagent une définition, mais gardent réglages et état indépendants. La corbeille masque le code ; la purge exige une définition en corbeille sans instance vivante. Les instances supprimées peuvent conserver une référence purgée et affichent « Widget indisponible » après restauration.

Bornes provisoires : 100 définitions par projet, corbeille comprise ; 64 Kio UTF-8 par champ HTML/CSS/source/compilé, 256 Kio par définition ; réglages JSON plats de 4 Kio (scalaires ou tableaux de scalaires), état JSON de 8 Kio, profondeur 8 et 2 048 nœuds maximum. Les contrôles serveur font autorité. Export paginé et nettoyage par petits lots incluent `gmCustomWidgets`. Les inventaires vérifient les références conservées et les fixtures E2E contiennent définition et instance non vides.

Sucrase **3.35.1**, épinglé, est importé dynamiquement dans le navigateur au lancement de l’aperçu ou à l’enregistrement TS. `transform(source, { transforms: ['typescript'], disableESTransforms: true })` retire les types ; aucun code utilisateur n’est évalué sur le serveur. Ce n’est pas une vérification de types ni un résolveur de modules. Les imports externes restent interdits. Context7 étant indisponible, API et options ont été vérifiées dans les types et le README installés de cette version, ainsi que dans le [changelog officiel, entrée 3.35.1](https://github.com/alangpierce/sucrase/blob/main/CHANGELOG.md#3351-2025-11-19). Une erreur de compilation bloque l’enregistrement.

## Frontières du navigateur

L’application charge `/sandbox/host`, document brut de même origine, sans React, jeton ou hydratation. Le relais ne contient aucun code utilisateur. Sa CSP limite `frame-src` à l’origine applicative et au chemin `/sandbox/runner` ; elle refuse ainsi les navigations du runner vers d’autres chemins, origines et schémas, y compris `data:`. Le runner est un second document brut dans `sandbox="allow-scripts"`, sans `allow-same-origin`, sans permissions et sans referrer. Il ne peut lire cookies, stockage ou DOM parents, ouvrir des fenêtres ou naviguer le haut.

Les deux bootstraps sont des sources statiques versionnées F8.1 ; le serveur calcule SHA-256 sur la chaîne effectivement insérée dans chaque balise script. Aucun hash écrit à la main. Seule la réponse GET réussie des deux chemins exacts reçoit ses en-têtes spécifiques dans `src/server.ts`. Toutes les erreurs et les autres chemins conservent la CSP applicative et `DENY`. Les documents sont `private, no-store` ; « immuable » désigne ici leur contenu sans données utilisateur, pas un cache partagé. Le relais n’a pas `unsafe-eval`. Le runner autorise uniquement l’empreinte de son bootstrap et `unsafe-eval`, jamais `self`, pour exécuter le code dans son origine opaque. Les scripts externes, fetch, workers, sous-cadres et formulaires sont refusés par CSP. HTML et CSS utilisateur sont injectés dans le runner seulement ; les erreurs remontent comme texte tronqué à 500 caractères.

Le runner accepte une seule initialisation, de sa fenêtre parent et de l’origine applicative configurée. Un MessageChannel neuf appartient à chaque génération ; tous les autres échanges passent sur son port privé. Les échanges application/relais exigent source et origine exactes, avec origine cible explicite. Les schémas Zod partagés protègent la frontière application ; les documents bruts embarquent les mêmes contrôles structurels et limites sans importer de bibliothèque. Les tests exécutent les bootstraps réels. Rechargement, suspension et démontage ferment les canaux.

Le relais et l’application imposent séparément les budgets : état 10/s, taille 5/s, erreur 5/s, total 30/s, y compris messages invalides. Dépassement : retrait du runner et bouton de rechargement. Ping toutes les 2 s, suspension après 5 s sans pong (au prochain tick). La persistance conserve le dernier état, au plus une fois par seconde, avec une seule mutation en vol et `expectedVersion`. Un conflit ou refus de quota arrête les sauvegardes et s’affiche ; aucune réécriture aveugle. `customWidgets.saveState` ne crée pas d’historique et consomme uniquement `customWidgetWrite`, 30/min par compte sur quatre shards. L’aperçu n’a aucun callback de persistance ; lecture seule et impression désactivent le writer et annulent son état en attente. L’impression recrée le runner en mode `static`, avec HTML et CSS de base et API permettant un rendu adapté.

## Limites assumées et preuves

`webrtc 'block'` complète la suppression préalable des constructeurs `RTCPeerConnection`, `webkitRTCPeerConnection`, `RTCDataChannel` et `RTCIceTransport`. Les documents `about:blank` héritent de la CSP. Chromium est le navigateur de preuve CI, avec un serveur UDP STUN local : aucune interception HTTP ne suffit à prouver l’absence d’ICE. Un navigateur ignorant `webrtc` pourrait conserver une sortie ICE si un constructeur restait accessible ; aucune garantie universelle n’est annoncée.

La sonde locale sur le Chromium installé indique que `webrtc` est une directive inconnue ; les suppressions de constructeurs, le sandbox hérité et les permissions restent donc indispensables. La même sonde a observé zéro paquet UDP, y compris après tentative via `about:blank`. Cela ne remplace pas la preuve complète CI. Une navigation refusée peut remplacer le runner par `chrome-error://chromewebdata/` : le relais suspend cette génération et chaque tentative E2E utilise un cadre neuf.

Une boucle infinie peut figer l’onglet si le navigateur ne sépare pas les processus. Le watchdog n’est pas une limite CPU ; son efficacité dépend de l’isolation du runner. La spec CI consigne le comportement Chromium et exige un Screen utilisable ou une suspension. La sonde locale a conservé un parent utilisable, mais aucun signal de suspension après 12 s : relais et runner peuvent partager le processus bloqué. Une origine de sandbox sur un site distinct reste une évolution possible, hors F8. La CSP est une défense de navigateur, pas un moteur d’exécution avec quotas mémoire.

Les E2E ciblent le serveur construit : TS, état après rechargement, aperçu/statique, en-têtes finaux et empreintes, sondes d’évasion, navigations, attaques entre cadres custom/F7b, flood sans consommation du quota de notes, STUN UDP et boucle infinie. Ces preuves doivent être exécutées en CI ; le poste de construction n’a pas Docker. Les tests backend, navigateur et outils locaux ne remplacent pas ces preuves de transport.
