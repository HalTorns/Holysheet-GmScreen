# Fichiers de projet (F6)

Décision du 2 novembre 2026, contrat [PLAN-F6](../PLAN-F6.md).

Les fichiers privés résident dans le stockage Convex. `gmFiles` relie un blob unique au propriétaire stable et à son projet ; les widgets `image` et `pdf` référencent cette ligne. Les copies de widgets et de Screens partagent le fichier. Un widget sans sélection, purgé, en corbeille ou dont le fichier appartient à un autre projet affiche « Fichier indisponible ».

Une seule entrée d’import existe : `POST /files/upload` sur l’origine site Convex. Le navigateur réutilise le `fetchAccessToken` du provider d’authentification ; aucun bearer n’est persisté. CORS et préflight acceptent exclusivement `SITE_URL`. Le rate limiter authentifié (10 imports/minute, capacité 10), puis une query interne avec `requireUser` et contrôle du projet précèdent la lecture. `Content-Length` est obligatoire ; le flux est lu jusqu’à 16 Mio au maximum. Les signatures PNG, JPEG, WebP, GIF et PDF déterminent le type canonique du nouveau Blob ; le nom et le MIME déclarés ne participent jamais à cette décision. SVG est refusé. Ces signatures ne prétendent pas garantir la validité complète d’un document ; un document malformé affiche une erreur de rendu.

Limites initiales réversibles : 10 Mio par image, 16 Mio par PDF, 500 Mio par compte, 200 fichiers par projet, corbeille comprise. La mutation finale revérifie `requireUser`, le projet et les deux budgets. `gmFileUsage`, compteur par propriétaire indexé et transactionnel, évite un scan sans borne de tous ses projets ; il est exporté, nettoyé et vérifié à la restauration avec les fichiers. Les imports concurrents lisent et écrivent cette même ligne. Une insertion refusée supprime son blob ; un cron paginé supprime les blobs orphelins âgés de plus d’une heure après un éventuel crash. **Toute future utilisation de `_storage` doit enregistrer ses blobs dans une table connue du cron** avant d’être activée.

La lecture contrôlée passe par une query propriétaire liée au widget et au projet. Les URL de `getUrl` sont des capacités : toute personne possédant une URL peut lire le blob. Ce risque est accepté pour la bêta privée ; la purge invalide l’URL, la simple mise en corbeille masque le widget mais ne révoque pas une URL déjà obtenue. Aucun fichier n’est ouvert par navigation. L’image est rendue par `<img>` ; PDF.js reçoit les octets et dessine un canvas. La CSP autorise l’origine cloud dans `img-src`, cloud et site dans `connect-src`, et les workers locaux dans `worker-src`.

PDF.js est épinglé en `pdfjs-dist` 5.4.624 : ses types installés et sa [source officielle versionnée](https://github.com/mozilla/pdf.js/blob/v5.4.624/src/display/api.js) acceptent `isEvalSupported: false`, contrairement aux versions 6 examinées. Son moteur Node `>=20.16.0 || >=22.3.0` admet Node 26.12.0. Le module et le worker local sont chargés dynamiquement par Vite. Aucun moteur JavaScript de PDF, iframe, extraction ou OCR. Le rendu statique conserve l’image ou la première page PDF ; F9 reste hors périmètre. Context7 était indisponible : API Convex 1.46.0 et PDF.js contrôlées dans les types/sources installés et les documents officiels.

La bibliothèque permet renommage, corbeille, restauration et purge seulement depuis la corbeille. La confirmation de corbeille compte les widgets concernés par pages ; une référence ne bloque jamais la purge. L’export de compte contient uniquement les métadonnées, sans octets ni URL de téléchargement ; la sauvegarde opérateur avec `--include-file-storage` inclut les blobs. Le nettoyage de compte supprime lignes et blobs via `cleanupJobs`, par lots bornés.
